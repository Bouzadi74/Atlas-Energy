# Kafka telemetry: Bronze, Silver, and quarantine

This is a synthetic demonstration stream for the academic Atlas Energy platform. There is no
approved Moroccan utility telemetry feed in the source registry. The events generated by
`atlas-publish-demo-telemetry` are `SYNTHETIC` and must never be described as SCADA, metered output,
or a 2024 historical observation. The stream does not change optimizer inputs or published KPIs.

## Contract and lineage

`kafka/schemas/telemetry-v1.schema.json` and `configs/streaming/telemetry.yml` define the event
shape and the currently approved producer/source. The topic is `atlas.telemetry.v1`. Event IDs are
UUIDs. The Kafka key and envelope key must match `payload.asset_id`. Supported metrics are
`generation_mw`, `demand_mw`, and `state_of_charge_mwh`, all nonnegative. Power values use MW;
state of charge uses MWh. Times must include an offset and are normalized to UTC.

The Spark job creates three Delta tables:

1. `data/bronze/telemetry/kafka`: original Kafka key/value bytes, topic, partition, offset, broker
   timestamp, and ingestion timestamp. The Delta log and stream checkpoint make this replayable.
2. `data/silver/telemetry_events`: one accepted event ID, normalized fields/units, event and
   ingestion times, provenance class, and Bronze Kafka coordinates.
3. `data/silver/telemetry_quarantine`: original bytes and Kafka coordinates plus a specific
   rejection reason. Malformed JSON, unsupported versions, unapproved sources, bad keys, missing
   fields, bad units, and invalid values land here.

The natural key for Bronze and quarantine is `(topic, partition, offset)`; Silver uses `event_id`.
Silver applies a 24-hour event-time watermark and deduplication, then an insert-only Delta merge
prevents duplicate IDs on restart or replay. Separate checkpoint directories exist for Bronze,
Silver, and quarantine under ignored `data/checkpoints/telemetry/telemetry-v1/`. Preserve those
directories together with the tables. Never delete checkpoints to force a replay against an
existing table without an explicit recovery procedure. Kafka offset gaps fail the Bronze query.

## Local demonstration

Start Kafka and install the data environment/JDK 21 as described in `README.md`. Spark's Kafka
connector is fetched from Maven on the first run; the command selects the connector version that
matches installed PySpark. Then publish a deterministic synthetic batch and process available data:

```powershell
docker compose up -d kafka
uv sync --extra dev --extra data
$env:JAVA_HOME = "C:\Program Files\Eclipse Adoptium\jdk-21.0.7.6-hotspot"
$env:PATH = "$env:JAVA_HOME\bin;$env:PATH"
$demoBatch = "demo-$([guid]::NewGuid().ToString('N').Substring(0,8))"
$demoStart = (Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:00:00Z")
uv run atlas-publish-demo-telemetry --batch-id $demoBatch --start $demoStart --count 3 --include-invalid
uv run atlas-stream-telemetry --once
```

The sample creates three valid events and one deliberately invalid negative value. The invalid
event should appear in quarantine with `invalid_value`. Running the producer again with the same
batch ID and start time intentionally sends duplicate event IDs; the Silver count should remain
three. A
`--once` run writes a manifest under `data/silver/manifests/telemetry/` with table versions, row
counts, Kafka offset ranges, quarantine reasons, and checksums of the configuration and schema.
To follow new messages continuously, run `uv run atlas-stream-telemetry` in its own terminal.

Check counts in PowerShell:

```powershell
uv run python -c "from atlas.transforms.telemetry_stream import build_spark_session; s=build_spark_session('atlas-telemetry-check'); print('bronze', s.read.format('delta').load('data/bronze/telemetry/kafka').count()); print('silver', s.read.format('delta').load('data/silver/telemetry_events').count()); print('quarantine', s.read.format('delta').load('data/silver/telemetry_quarantine').count()); s.stop()"
```

Quarantine records require review; this pipeline does not invent replacement values. Before any
real feed is added, register its source/permission/retention contract, extend the allowed producer
and source IDs, and define metric-specific quality thresholds and a new contract version.

The local replay check on 3 October 2026 produced 8 Bronze records, 3 unique Silver records, and
2 quarantined `invalid_value` records after publishing the same four-message batch twice. Spark
emitted a Windows temporary-directory cleanup warning after a successful Delta commit; the query
completed with exit code zero and the independent table counts reconciled.

## Operational limits

This is a local Spark Structured Streaming path. It has checkpointed ingestion and lineage, but
no production telemetry source, schema registry service, alert routing, dedicated streaming
cluster, or end-to-end recovery automation. A reused event ID with a changed payload is currently
deduplicated, not separately flagged as a conflict; add a collision audit before admitting a real
publisher. Kafka and Spark progress can be inspected through their local UIs/logs; production
lag/throughput gauges remain to be integrated into monitoring.
